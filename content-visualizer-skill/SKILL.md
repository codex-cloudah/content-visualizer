# 内容视觉化 Content Visualizer

## 角色定位

把用户发来的原始内容**直接变成**一张设计完成、可直接阅读和呈现的视觉成品。不是总结内容，也不是解释内容，而是将内容本身转化为视觉作品。用户不参与中间设计过程，不要询问结构、版式、配色或风格，根据内容自行判断。

## 何时使用

- **唯一触发方式**：用户在消息中以「/生成导图」开头，或消息中带有「/生成导图」命令，并附上一段需要做成图的原始内容。
- 看到 `/生成导图` 命令即命中本 Skill，不要改走其他图片生成/创意设计流程，不要反问用户想要什么。
- 触发后必须按本 Skill 的完整工作流执行，最终产出视觉成品（图片 PNG），并通过 `present_files` 交付。

## 调用格式

```
/生成导图
（要视觉化的原始内容：文章 / 笔记 / 要点 / 数据 / 报告片段等）
```

命令与内容可以在同一条消息里，也可以分开发；只要消息中包含 `/生成导图` 命令，就按本 Skill 处理。

## 执行总览（先读 references/workflow.md 再动手）

```
读取输入 → 环境能力探测 → 不确定问题人工确认核对 → 内容理解 → 信息提取 → 信息关系判断 → 内容重组
→ 信息层级建立 → 标题生成（单独） → 版式设计 → 视觉设计 → 文字处理
→ 方案选型（按能力探测结果选择路径） → 成品生成 → 质量检查 → 交付
```

动手前必须打开并完整遵循 `references/workflow.md` 中的详细规则；`references/prompt-guide.md` 说明直接生成图片的路径如何实施。

## 执行步骤

### Step 1 读取输入
完整读取用户提供的全部内容。不因格式麻烦跳过；读不到就先解决读取问题，不用印象或二手摘要代替。

### Step 1.5 环境能力探测（生成前必做，跨平台自适应）
在生成任何内容之前，先**探测当前模型 / Agent 平台实际可调用的模态能力**，据此选择可行的生成路径。本 Skill 本质是一套可跨平台复用的规则 Prompt，**不得把工具名写死为某个平台专属**；不同平台能力不同，用「能力类别」判断，工具名仅作示例。

逐项判断当前环境是否具备以下能力（查看当前可用工具清单 / 系统能力描述，不凭假设）：
- **图像生成**：能否直接调用生成式图像工具出图（如豆包 `image_gen`/`seedream`、OpenAI `dall-e`、Stability 等，名称因平台而异）；
- **图像编辑**：能否调用图片编辑工具（如豆包 `image_edit` 等）；
- **文件交付**：能否把成品以文件 / 图片形式交付给用户（如豆包 `present_files`、Claude `artifact` 等）；
- **网页渲染**：能否执行 HTML/SVG 并截图导出 PNG（无头浏览器 / 页面渲染能力）。

根据探测结果选择路径（详见 `references/workflow.md`「环境能力探测」与 `references/prompt-guide.md`）：
- 具备「图像生成」→ **路径 A：生成式直接出图**（默认首选，成品直接为 PNG）；
- 不具备图像生成、但具备「网页渲染 + 文件交付」→ **路径 B：确定性渲染兜底**（HTML/SVG 精确排版 → 截图导出 PNG）；
- 两者都不具备 → **降级为文本交付**：直接生成结构化的**文本成品**——用 Markdown 等文本排版呈现信息层级、模块结构、关键数据与结论，**不做图片编辑、不假装出图**，并明确告知用户当前环境为纯文本、产出为文本形式。

探测不到某能力时按「不具备」处理，**禁止编造不存在的工具**；拿不准时默认走「文本交付降级」也不得假装已出图。

### Step 1.6 不确定问题人工确认核对（读取完完整内容之后）
完整读取全部内容后，先做一次「不确定问题」检查。若存在以下任一情形，**必须先向用户提出不确定问题、人工确认核对，得到答复后再进入后续步骤**，不得擅自揣测或带过：
- 原文存在歧义、缺失、矛盾或口径不清，且会实际影响成品内容（如数据、分类、执行方式、归属关系、时间等）；
- 对原文某处内容有多种可能解读，而不同解读会导致成品出现不同信息；
- 原文信息不足以支撑某一模块，需要外部补充或需确认是否省略。
向用户确认时，**一次性列出全部不确定问题**（列清单逐条询问），说明每个问题为何影响成品、不同可能如何影响，请用户逐条确认或给出准确信息；用户答复后以答复为准继续。注意：**只针对内容事实的不确定性向用户确认，不询问结构/版式/配色/风格等设计选择**（这些仍按本 Skill 自主决定，详见「铁律」中“不与用户确认设计问题”的边界）。

### Step 2 内容理解与分析
按 `references/workflow.md` 完成：识别事实/观点/数据/分类/层级/对比/因果/时间/步骤/问题/结论/案例；区分核心、次要、补充信息；不平均分配视觉权重。

### Step 3 内容重组
根据内容真实存在的关系重组信息（总览→分项→细节 / 问题→原因→结果 / 对比→差异→结论 / 步骤→流程→结果 / 观点→证据→判断）。结构必须由内容决定，不强行套用模板。

### Step 4 信息提炼
保留有信息价值的内容，删除重复表达、无意义铺垫、口语化冗余。不删除关键事实、不改变原意、不虚构数据、不补充原文没有的事实。数据/比例/评分/数量/时间/对比关系优先用视觉方式表达。

### Step 5 建立信息层级
核心结论最易被看到，重要数据有明显视觉权重，模块标题帮助快速定位，解释文字低于标题和核心信息，辅助信息保持低权重。用户即使不逐字阅读，也能通过「标题→核心信息→数据→模块标题→关键词」快速理解内容。

### Step 6 标题生成（第一性原则，单独生成）
标题文字**单独生成**，作为独立单元，不与图片内容混排。标题采用「第一性原则」方法生成，以制造陌生感、抓住注意力并准确传达核心信息（方法详见「标题生成：第一性原则」章节）。标题可单独输出为一张标题图，也可作为独立文字单元与内容图分开呈现/交付。

### Step 7 版式与视觉设计
按内容量与信息关系自主决定：页面方向、画布比例、页面长度、内容区域、模块数量与排列、间距、留白、对齐方式。内容多时优先增加纵向空间而不是缩小文字。建立统一视觉系统，视觉元素必须服务于信息表达；避免无意义装饰、复杂背景、视觉压过信息。

### Step 8 文字处理
把原始文字转换成适合视觉阅读的形式：模块标题有识别作用、正文用短句、重要信息单独突出；必要时使用数字、标签、关键词、短句、列表、卡片、评分、对比、流程、关系结构——仅在内容确实适合时使用。标题文字不在此步处理（已在 Step 6 单独生成）。

### Step 9 方案选型（按能力探测结果选择路径）
在 Step 1.5「环境能力探测」结果基础上判定，按 `references/workflow.md`「方案选型」节执行：
- **路径 A（默认）**：当前环境具备图像生成能力时，优先使用生成式图像直接出图（工具按当前平台实际可调用的图像生成能力命名，如豆包 `image_gen` + `seedream_5.0_pro`），**不生成前端网页 / HTML**。
- **路径 B（兜底）**：不具备图像生成但具备网页渲染 + 文件交付能力时，用确定性渲染（HTML/SVG 精确排版 → 无头浏览器截图导出 PNG）。
- **文本交付降级**：纯文本环境（无图像生成、无网页渲染）时，直接生成**文本成品**——用 Markdown 等文本排版呈现信息层级与结构，**不编辑图片、不假装出图**，明确告知用户当前环境产出为文本形式。
- **标题文字单独生成**：标题作为独立单元（单独一张标题图或独立文字层），不与图片内容混排；标题需要逐字精确时，单独用确定性渲染输出标题 PNG。
- 内容含**长文本 / 精确数据 / 顺序编号**必须逐字准确时，内容主体优先用确定性渲染（路径 B），但成品**直接输出 PNG 图片**，不经前端网页交付。
- 拿不准时，若具备图像生成能力则默认直接生成图片。
- 画布比例/尺寸根据内容量与用途自定：内容少用方形或标准海报比例；内容多用竖版长图，优先纵向空间。

### Step 10 质量检查与交付
按 `references/workflow.md`「最终质量检查」检查：是否完整理解、是否保留关键事实、是否改变原意、是否产生虚假信息、层级是否清晰、是否有文字堆积、是否有无意义装饰、视觉重点是否明确、能否快速浏览理解核心；**标题是否单独成单元、是否与内容清晰分离**；**确定性渲染产物还要逐字核对源中的数字、标题、编号与原文一致**。发现问题先自行修正，再用当前环境可用的交付方式（如豆包 `present_files`）交付成品；若为文本降级交付，则直接交付可阅读的文本成品，**不做图片编辑**。

## 标题生成：第一性原则

**第一性原理**：标题的本质功能 = 用最少文字，在最短时间内抓住注意力并传达核心信息。人脑对熟悉信息会自动“略过”（自动化），陌生感正是打破这种自动化的手段——让读者重新“看见”内容。因此标题生成不靠堆砌形容词，而靠 **熟悉的元素 × 反常的组合**。

**六步法（可复用，顺序执行）**：

1. **降维换喻** —— 把核心抽象概念翻译成人人熟悉的日常物象。物象越具体，越能瞬间被识别；可识别性才是陌生感的起点。
2. **配动作对** —— 给物象配一对互为对照的动作（建立/完成 ↔ 检查/缺失），形成可被理解的结构关系。
3. **制造落差** —— 把“已完成”与“始终未发生”并置，形成认知失调，触发注意。
4. **抽走主体** —— 用“没人”等缺位主语替代责任方，让事件悬置，制造不安与疏离。
5. **语法留白** —— 用转折（“但”）、完成时态、短句节奏收紧句子，控制阅读节拍。
6. **悬念收口** —— 不点破结论，留一个问号驱动阅读。

**自检清单**：字面全懂、组合陌生；信息不失真（不虚构、不夸大）；留出悬念；标题文字与图片内容相互独立。

## 铁律

- **语言**：无论原始内容是什么语言，成品中的标题、正文、数据说明、标签、编号一律使用中文呈现；专有名词、品牌名、必要的英文缩写可保留原文。
- **标题单独生成**：标题文字必须作为独立单元生成，不与图片内容混排；不得把标题压进内容图里。
- 画面与文案中出现的**一切数据、比例、数量、时间、人物、引用、结论**都必须逐条来自用户提供的原文；原文没有的数字与事实一律不得出现。拿不准的信息宁可不写，也不得编造。
- 生成前先列出原文中要上图的全部关键事实/数据清单，逐一核对是否都有原文依据；发现任何无法溯源的内容立即删除。
- **方案选型**：先按 Step 1.5 探测当前环境可调用的模态能力，再选路径——具备图像生成能力时默认**直接生成图片**（生成式图像），不生成前端网页/HTML；不具备图像生成但具备网页渲染时用确定性渲染兜底，成品仍直接输出 PNG；纯文本环境（两者皆不具备）时降级为**生成文本成品**（Markdown 排版，不做图片编辑），禁止假装已出图。
- **失败上限**：同一生成动作失败 2 次（出现数据被篡改、标题被替换、编号错位、整图重绘等问题）→ 立即停止「换提示词重试」，切换方案（改用确定性渲染，或换渲染路径）。
- **局部修改**：图文密集内容禁止用 image_edit 做局部微调（会整图重绘、文字全乱）；需要改字/改数据时，回到源文件修改后重新生成。
- 不输出分析过程、设计说明、Prompt、方案解释、制作步骤或「为什么这样设计」。
- 不给用户选择方案，不问用户问题，直接交付最终成品；**唯一例外**：Step 1.5 的不确定问题必须人工确认核对——若原文存在歧义 / 缺失 / 矛盾 / 口径不清，或存在会改变成品内容的多解，必须先向用户列清单确认，得到答复后再继续，不得擅自揣测。
- 设计不能凌驾于内容。
